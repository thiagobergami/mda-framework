MDA Studio

The operator surface for the MDA Spec Framework. A web UI that shows the MDA spec tree as the home for every game, with live issues, costs, validator warnings, approvals, and activity.

Mental model

The MDA spec tree is the application. Issues, agents, costs, and approvals are properties of nodes on that tree — not first-class objects you navigate to.

What it is

The studio is the running service that complements the file-based spec framework. Specs live in markdown under specs/ and design/; the studio owns the operational state that doesn't belong in version control: open issues, MTD spend, validator warnings, approvals, activity history, and live agent run status.

Operators come here to:

  • Survey a game's design state across all six MDA layers at once
  • See which specs have active work, who owns it, and what it's spending
  • Triage validator warnings and pending approvals
  • Investigate cost spikes by drilling into a subtree
  • Filter the tree to one agent / status / layer to focus

Operators can author specs from the UI — the empty-tree CTA and the "+" buttons on tree rows POST to /api/games/:id/specs, which drives mda new --from-json --no-prompt --json via the mda-runner. The resulting file lands in the workspace on disk and the spec-watcher publishes a node-changed SSE event so the tree updates without a reload. For deep authoring (large bodies, fine-grained edits) the CLI / wizard are still the better tool.

One engine, two front doors

You author at the keyboard          You drive a UI for the team
       v                                    v
+---------------+                    +------------------+
|  mda CLI      |  <-- subprocess -- |  @mda-studio/    |
|  npm run spec |       via          |  server          |
|  edit *.md    |     mda-runner     |  & ui            |
+---------------+                    +------------------+
       |                                    ^
       v                                    | reads + writes
+---------------------------------------------------+
|  specs/  +  design/                               |
|  (markdown files, version-controlled)             |
+---------------------------------------------------+

The CLI is the authoring front door. The studio is the operating front door — but it never re-implements validators, gates, or scaffolding. Instead, the mda-runner service in @mda-studio/server spawns npx mda <cmd> --json as a subprocess and parses the output through zod schemas shared with the CLI. The result: a Validate button in the chrome runs the same code as npx mda validate at your terminal; a "+" CTA on a tree node runs the same code as npx mda new.

See Decisions · D0.1 for why the framework went hybrid rather than studio-first.

What you get on the screen

The home for any game is its spec tree. Every row shows: 

LAYER_GLYPH  SPEC_ID  TITLE                STATUS  COST_ROLLUP  ASSIGNEE  WARN?
  |            |       |                     |       |           |         |
  |            |       |                     |       |           |         L  N
  |            |       |                     |       |           +- @agent
  |            |       |                     |       +- $12.40 (MTD subtree)
  |            |       |                     +- glyph for status
  |            |       +- from spec frontmatter title
  |            +- canonical id (MEC-001, AES-003, ...)
  +- A | D | M | AST | TUNE | LEVEL

Clicking a row opens a right-side drawer with six tabs covering the spec body, active and historical issues, comments, work products, costs, and the upward trace.

Chrome surfaces

Beyond the tree + drawer, the chrome bar carries five secondary surfaces. They open over the tree (URL view=...) so a single Esc returns you home.

✅

Approvals

Pending approvals across the studio, with inline approve/reject.

📊

Costs detail

Layer rollup, top spec spenders, recent events. Scopable to any subtree from the drawer.

👨

Observed assignees

Read-only roster of every assignee handle seen across issues, grouped by primary MDA layer. (Agents appear here once M3 lands.)

🎨

Asset plans

One row per design/asset-plans/<asset-id>/ with state from disk plus Generate / Exec / Import buttons that drive the CLI subcommands through mda-runner.

⚙

Settings

Studio-level configuration shell: secrets, plugins, scheduled routines.

🗡

Activity

Slide-out log of recent studio events — issue changes, approvals, costs, validator runs.

Live updates

The UI subscribes to a Server-Sent Events stream (GET /api/studios/:id/events). Any mutation in the server publishes a node-changed, issue-status-changed, cost-event, validator-run-completed, or approval-changed event; the UI invalidates the relevant fetched data without a page reload.

Key features

🏠

Spec-tree home

The MDA tree itself is the home screen for every game, not a side panel.

🔍

Composable lenses

Filter by agent, status, layer, warnings, or free text — combined with AND, ancestors stay visible.

⌨

Keyboard-first

Arrow keys navigate the tree, ⌘K opens a fuzzy palette, ? shows the keymap.

🔗

Deep links

Every panel, drawer, and filter is in the URL. Share a link, get the exact view.

⚡

Live SSE updates

The tree, drawer, badges, and activity feed all stay current without polling.

🧮

Fixture fallback

If the API is down, the UI renders a bundled fixture so the surface never goes blank.

Boot it

From the mda-studio/ workspace:

# first-run housekeeping (creates the embedded pglite instance)
pnpm install
pnpm mda-studio onboard --yes

# terminal 1 - API at 127.0.0.1:3100
pnpm --filter @mda-studio/server dev

# terminal 2 - UI at 127.0.0.1:3101 (proxies /api -> 3100)
pnpm --filter @mda-studio/ui dev

Visit http://127.0.0.1:3101, fill in Register a game with a path to a folder containing specs/concept/<game>.concept.md, and click Register. The studio scans the workspace, starts a spec-watcher, and renders the live tree.

Prerequisites

Node.js ≥ 20 and pnpm 9.x. The studio is its own pnpm workspace under mda-studio/, distinct from the npm-based repo root. Always run pnpm commands from mda-studio/.
