Getting Started

Install the framework, scaffold your first game concept, and validate it in under 5 minutes — either at the keyboard, in the browser, or both.

Prerequisites

  • Node.js ≥ 18 for the CLI and Spec Wizard.
  • npm (comes with Node.js).
  • For the MDA Studio: Node.js ≥ 20 and pnpm 9.x (the workspace pins pnpm@9.11.0).

Install

git clone <this-repo>
cd framework
npm install

Installs the mda CLI and the wizard's dependencies. There is no build step. The bin field in tools/package.json points at tools/bin/mda.cjs, a tiny shim that runs tools/src/cli.ts through tsx. Editing tools/src/*.ts and re-invoking npx mda picks up the change immediately.

Choose a front door

The framework has two equally-valid entry points that share one engine. Pick one to start; you can switch any time.

Path A — Authoring solo (CLI)

The fastest path from "I have a game idea" to "I have validated specs". One install at the repo root, no service to keep running.

  1. Launch the wizard 
    npm run spec

    The wizard walks Concept → Aesthetics → Dynamics → Mechanics → Assets → Tuning → Levels, branches its menu off what already exists under specs/, and pre-fills frontmatter from your answers. Hand-author at any point with npx mda new <layer> "<name>".

  2. Validate 
    npx mda validate

    Runs every rule across specs/ and design/levels/. Exit 0 on pass.

  3. Run a quality gate 
    npx mda gate concept

    Gates check the markdown body, not just frontmatter. They tell you whether a layer is complete enough to author the next one.

  4. (Optional) Generate an asset plan 
    npx mda asset-plan generate AST-001

    Reads the asset spec, the concept, the aesthetic specs it traces to, and the style guide; emits design/asset-plans/AST-001/AST-001.v1.plan.md. See the CLI reference for exec, import, and the NDJSON event stream that powers the studio's progress UI.

Path B — Operating with the studio

The studio is a small Express + React service under mda-studio/ that holds operator state the CLI can't: registered games, issues, costs, approvals, asset-plan execution. Reach for it when more than one person needs the same view or when state has to survive a restart.

  1. First-run housekeeping 
    cd mda-studio
pnpm install
pnpm mda-studio onboard --yes

    mda-studio onboard resolves the embedded instance directory (~/.mda-studio/instances/default/), opens a pglite database under it, runs a smoke query, and prints the next-step commands.

  2. Start the API and the UI 
    # terminal 1 - API on 127.0.0.1:3100
pnpm --filter @mda-studio/server dev

# terminal 2 - UI on 127.0.0.1:3101 (proxies /api -> 3100)
pnpm --filter @mda-studio/ui dev
  3. Open http://127.0.0.1:3101 and register a game

    The home screen shows a Register a game form. Point it at any folder that contains specs/concept/<game>.concept.md. The studio indexes the workspace, starts a chokidar spec-watcher, and adds a card to the home grid. Clicking it renders the live spec tree.

  4. Drive the engine from the UI

    Once your game is registered, the chrome's Validate button calls mda validate --json via the mda-runner subprocess driver and surfaces diagnostics as warning badges on the affected spec rows. The "+" CTAs on tree nodes scaffold new specs via mda new --from-json. The Asset Plans panel ships Generate / Exec / Import buttons per asset.

Mixing the two paths

You don't have to pick. Authors typically use the wizard for the first cascade, then keep the studio open in a tab to track issues and validator warnings while they iterate. Because the studio drives the same CLI you'd use at the keyboard, the two paths never disagree.

The dogfood example

The repo ships a full M / D / A cascade as its dogfood reference: Cozy Hide and Seek, a 60-second hide-and-seek round for 2–4 friends. Read it as the canonical example of what a validated specs tree looks like:

  • specs/concept/cozy-hide-and-seek.concept.md — the root
  • specs/aesthetics/round-fellowship.aes.md — primary aesthetic (AES-001)
  • specs/dynamics/round-tension-loop.dyn.md — the 60-second loop (DYN-001)
  • specs/mechanics/round-lifecycle.mec.md — the state machine (MEC-004)
  • specs/tuning/round-and-actions.tune.md — every tunable parameter (TUN-001)
  • specs/assets/cozy-hiding-spot.asset.md — the hiding-spot variants (AST-001)
  • design/levels/sunlit-den.level.md — the playable arena (LVL-001)

Run npx mda validate from the repo root; the cascade exits 0. The friction surfaced while authoring it lives at design/decisions/2026-05-27-dogfood-log.md and feeds the next round of CLI / wizard / schema fixes.

Project Structure

specs/                              # Canonical M/D/A truth
├── WORKFLOW.md                     # 8-step process: idea -> implementation
├── glossary.md                     # Shared MDA vocabulary
├── traceability.md                 # Bidirectional links between all specs
├── concept/                        # Game vision, aesthetic profile, feature map
├── aesthetics/                     # Player experience goals (observable proxies)
├── dynamics/                       # Feedback systems, invariants, interaction patterns
├── mechanics/                      # Player affordances, rules, behavioral contracts
├── tuning/                         # Parameter ranges, trade-offs, iteration logs
├── assets/                         # Emotional intent, technical reqs, placeholders
└── bindings/                       # Engine-specific specs (parked: multi-engine deferred)

design/                             # Iterative artifacts that consume specs
├── decisions/                      # ADRs (front-door, embedded DB, dogfood, ...)
├── levels/                         # Spatial layouts, beat charts, encounters
├── roadmap/                        # Parked roadmaps
├── walkthroughs/                   # Scripted authoring passes
├── asset-plans/                    # MCP-driven asset implementation pipeline
└── pipeline/                       # `npm run spec` wizard

tools/                              # The `mda` CLI (TypeScript, run through tsx)
├── README.md                       # Machine-readable JSON contracts
├── bin/mda.cjs                     # Shim that runs src/cli.ts via tsx
└── src/                            # No build step
    ├── cli.ts                      # Commander entry point
    ├── scaffold.ts                 # Spec template generation + override merge
    ├── asset-plan/                 # Pipeline (generate/exec/import/list)
    ├── rules/                      # Validation rules
    └── gates/                      # Quality gates

mda-studio/                         # Operator surface (pnpm workspace)
├── server/                         # @mda-studio/server (Express + mda-runner + spec-watcher)
├── ui/                             # @mda-studio/ui (React 18 + Vite SPA)
├── cli/                            # @mda-studio/cli (`mda-studio onboard`)
└── packages/
    ├── shared/                     # @mda-studio/shared (zod schemas, incl. CLI contracts)
    └── db/                         # @mda-studio/db (drizzle schema + pglite/pg client)

src/                                # Runtime tools (Luau)
├── shared/MDALogger.luau           # Structured logging with MDA layer tagging
└── tools/validate-specs.luau       # Legacy Luau spec validator

CLAUDE.md                           # AI instructions (read by Claude Code)

Working with AI

The framework is designed to be used with AI coding assistants, particularly Claude Code. The CLAUDE.md file in the project root contains comprehensive instructions that Claude reads automatically — including the rules for when to drive the engine from the studio versus authoring at the keyboard, and the persistence / runner contracts the studio depends on.

Tip

When using Claude Code, just describe your game idea. Claude will read the CLAUDE.md instructions, follow the workflow, create specs layer by layer, run gates, and implement the code — all while maintaining full MDA traceability.
