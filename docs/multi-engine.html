Multi-Engine Support

Status: deferred. Roblox is the only engine the framework targets today.

Why this is parked

The framework was designed for multi-engine work, but specs/bindings/ has no instances and no real game is asking for a second engine target yet. Multi-engine reopens when a real game ships against Roblox and a second-engine target arrives with a motivating game attached. Until then this page is reference, not roadmap.

The rule code (binding-coverage) and the equivalence tables below stay in tree so the work is cheap to revive. See Decisions · D0.2 and the parked roadmap at design/roadmap/multi-engine.md.

What "deferred" means in practice

  • Validator: the binding-coverage rule is excluded from allRules and parked under _deferredRules in tools/src/rules/index.ts. Re-enabling is a one-line change.
  • Specs: specs/bindings/ is empty. The binding schema stays documented so the shape is ready when the work resumes.
  • Logger: MDALogger ships as Roblox / Luau only (MEC-003 carries an explicit "Engine scope" note). Ports to Unity / Unreal wait on the same trigger.
  • Asset plans: engine profiles under design/asset-plans/_engines/ remain in tree so the plug-in shape is preserved; routing today only resolves roblox.

What stays as reference (when it reopens)

The original architecture intent and equivalence tables are preserved below so that whoever picks this back up has the starting point.

Architecture (parked)

  • Behavioral specs (specs/mechanics/, specs/dynamics/, etc.) are engine-agnostic
  • Binding specs (specs/bindings/) map behavioral contracts to engine-specific APIs
  • Equivalence table (specs/bindings/equivalence.md) provides a quick cross-engine reference

When implementing for a specific engine, read both the mechanic spec (what to build) and its binding spec (how to build it in your engine).
