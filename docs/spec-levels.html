Level Spec Schema

Level specs describe the spatial and temporal composition of a single level — geometry, pacing, encounters, sightlines, and optional content. Levels orchestrate existing M/D/A specs into a particular arrangement; they don't define new ones.

File pattern: design/levels/{slug}.level.md
ID format: LVL-{NNN}
Scaffold: npx mda new level "Tutorial Forest"
Schema source: design/levels/_schema.md

Why levels live in design/, not specs/

The MDA paper treats levels as content under Mechanics. In practice, a level orchestrates all three layers per zone — geometry that affords a mechanic, pacing that drives a dynamic feedback loop, and atmosphere that targets a specific aesthetic. A level spec references M/D/A primitives by ID rather than competing with them, so it lives in design/ alongside other iterative artifacts.

Vocabulary

TermMeaning
BlockoutWhitebox / spatial layout — geometry only, no art
Beat chartPacing curve over time: tension, rest, climax, release
EncounterA self-contained unit of mechanic interaction with success/fail states
AffordanceWhat the geometry teaches the player (ledge → climb)
SightlineWhat the player can see from key positions
Critical pathThe minimum traversal to complete the level
Optional pathBranches off the critical path that reward exploration

Frontmatter

---
id: LVL-{NNN}
name: {Descriptive name}
status: blockout | playable | polished
references:
  aesthetics: [AES-NNN, ...]
  dynamics:   [DYN-NNN, ...]
  mechanics:  [MEC-NNN, ...]
  assets:     [AST-NNN, ...]
estimated_duration: {seconds}
---

The references: block is parsed as traces by the validator — every referenced spec ID must resolve, and the level-references rule requires at least one AES, one DYN, and one MEC.

Required Sections

A level spec MUST contain all 11 sections, in this order:

  1. Player Goal — one sentence
  2. Aesthetic Targets — table of beat → aesthetic → reasoning
  3. Critical Path — ASCII or mermaid diagram
  4. Blockout — coarse spatial layout
  5. Beat Chart — pacing curve table (time, zone, tension, mechanic, aesthetic)
  6. Encounters — one or more, each with location, mechanic mix, expected dynamic, success/fail
  7. Affordances — geometry → player action → spec ID it teaches
  8. Sightline Notes — what's visible from each key position
  9. Optional Content — side paths and reward types (or "none")
  10. Open Questions — playtest items not yet resolved
  11. Iteration Log — date / change / why / observed effect

Status Transitions

StatusMeaningPromote when
blockoutGeometry placeholders only, traversable but uglyBeat chart and sightlines validated by walkthrough
playableFull geometry, real assets in place, encounters wiredInternal playtests pass; ready for art/audio
polishedArt, audio, and tuning passes completeReady for external playtest

Validator Rule: level-references

Source: tools/src/rules/level-references.ts. Errors when a level:

  • References no AES, no DYN, or no MEC spec
  • Has a status that isn't one of blockout / playable / polished

Authoring a Level

Use the wizard for guided authoring (recommended): npm run spec → "Design a level". The wizard prompts for status, traces, and duration, then patches them into the scaffolded file.

Manual scaffolding:

npx mda new level "Tutorial Forest"
# → design/levels/tutorial-forest.level.md (LVL-001 assigned automatically)
