CLI Reference

The mda CLI provides four commands for working with specs: validate, gate, new, and asset-plan. Every command emits machine-readable output when --json is set; the studio's mda-runner service relies on those contracts.

No build step

The bin field in tools/package.json points at tools/bin/mda.cjs, a tiny shim that runs src/cli.ts through tsx. Editing tools/src/*.ts and re-invoking npx mda picks up the change immediately — no tsc, no dist/.

mda validate — Check spec integrity

Runs validation rules against all specs to catch structural issues.

# Human-readable report across every scope under specs/
npx mda validate

# NDJSON output (one compact JSON object per scope) for CI or the studio
npx mda validate --json

# Validate a specific scope only
npx mda validate --scope specs

# Validate from a different project root
npx mda validate --dir /path/to/project

Validation Rules

RuleWhat it checksLevel
trace-resolutionAll traces_to_* and level references: IDs resolveerror
no-vacuoEvery MEC spec traces to at least one DYN specerror
asset-tracesEvery AST spec traces to a MEC (error) and an AES (warning)mixed
tuning-completenessEvery TUN spec traces to MEC + DYN + AESwarning
unique-idsNo duplicate spec IDs within a scopeerror
no-orphansEvery spec is referenced by at least one other spec (LVL exempt)warning
frontmatter-schemaRequired frontmatter fields are present per layerwarning
level-referencesLVL specs reference at least one AES, one DYN, one MECerror

Exit code is 0 on pass, 1 on any error-level diagnostic.

Multi-engine rule parked

The binding-coverage rule is excluded from allRules and stays under _deferredRules in tools/src/rules/index.ts while multi-engine is deferred. Re-enabling is a one-line change. See Decisions · D0.2.

Framework-Tool Exemption

Specs with scope: framework-tool are exempt from trace-resolution, no-vacuo, and orphan checks. This is for cross-cutting tools like the MDA Logger (MEC-003) that don't fit the normal M→D→A chain.

mda gate <layer> — Run quality gates

Quality gates verify that a spec is complete and well-formed enough to proceed to the next layer. Gates check the markdown body content, not just frontmatter. 

# Run the concept readiness gate
npx mda gate concept

# Run the aesthetic gate
npx mda gate aesthetic

# Override a failure with a logged reason
npx mda gate dynamic --override "Invariants pending playtest data"

# Fail the process on gate failure (useful in CI)
npx mda gate mechanic --strict

# Single compact JSON array of gate results
npx mda gate implementation --json

Available Gates

GateApplies toKey checks
concept GAME specs Vision clarity, aesthetic commitment (Primary + Absent tiers), core loop cycle, boundary definition, feature map, success criteria
aesthetic AES specs Measurable proxies with targets, anti-patterns defined, precise vocabulary (no "fun"), primary aesthetic classified
dynamic DYN specs Feedback loops with cycle notation, binary invariants (INV-N), degenerate dynamics named, traces to aesthetics
mechanic MEC specs Behavioral contract with I/O, testable acceptance criteria, player affordances listed, traces to dynamics
implementation MEC specs All mechanic checks + engine binding exists + upstream specs (DYN, AES) are present

Gate results are saved to specs/.gate-status.json for tracking.

Gates vs Rules

Rules check structural integrity (frontmatter, traces, IDs) and are always enforced.
Gates check semantic completeness (is the body content sufficient?) and are advisory by default. Use --strict to make gates enforced.

mda new <layer> <name> — Scaffold a new spec

Creates a new spec file from a template with auto-assigned ID and updates traceability.

# Scaffold specs at each layer
npx mda new concept "Lantern Woods"
npx mda new aesthetic "Forest Discovery"
npx mda new dynamic "Creature Reveal Cycle"
npx mda new mechanic "Lantern Interaction"
npx mda new tuning "Lantern Pacing"
npx mda new asset "Firefly Creature"
npx mda new level "Tutorial Forest"        # writes to design/levels/

Machine-readable mode

Used by the studio's runNew helper and by any external program that needs to scaffold specs without a TTY: 

echo '{"traces_to_dynamics":["DYN-001"]}' > /tmp/o.json
npx mda new mechanic "Lantern Interaction" \
  --from-json /tmp/o.json --no-prompt --json
# {"ok":true,"id":"MEC-007","file":"specs/mechanics/lantern-interaction.mec.md",
#  "layer":"mechanic","name":"Lantern Interaction"}
  • --from-json <path> — reads a JSON object of frontmatter overrides. Each key replaces the corresponding template field; the id field is scaffolder-owned and cannot be overridden.
  • --no-prompt — fails loudly on any missing required field instead of prompting. Currently advisory (the command is already non-interactive) but reserved so callers can declare they cannot answer prompts.
  • --json — suppresses all non-JSON output and emits a single compact line: {ok, id, file, layer, name} on success, {ok:false, error} on failure.

What it does

  • Assigns the next sequential ID for that layer (e.g., AES-002, LVL-003).
  • Creates the file at specs/{layer}/{slug}.{ext} (or design/levels/ for level).
  • Updates specs/traceability.md with a new row.
  • Merges any frontmatter overrides from --from-json.

mda asset-plan — Drive the asset pipeline

Walks an asset from "concept" through reference intake, plan generation, milestone execution, and engine import. See the design/asset-plans/ tree in the repo for the per-asset pipeline state. 

# List every asset and its current plan / executor state
npx mda asset-plan list

# Produce design/asset-plans/AST-001/AST-001.v1.plan.md (does NOT execute)
npx mda asset-plan generate AST-001

# Walk milestones with prompts after each; persists state
npx mda asset-plan exec AST-001

# Land the artifact in the engine after exec succeeds
npx mda asset-plan import AST-001

NDJSON event stream

Every subcommand accepts --json and emits one compact JSON event per line. The studio's UI parses this stream to drive its progress indicators. 

$ npx mda asset-plan generate AST-001 --json
{"event":"generate-start","ts":"2026-05-28T03:00:41.785Z","assetId":"AST-001"}
{"event":"plan-saved","ts":"2026-05-28T03:00:42.436Z","assetId":"AST-001",
 "path":"design/asset-plans/AST-001/AST-001.v1.plan.md","version":1}

Event vocabulary includes generate-start, intake-missing, plan-saved, exec-start, milestone-start, milestone-complete, mcp-unavailable, exec-complete, import-start, import-complete, and error. See tools/README.md for the full reference.

MCP fallback

When the MCP servers configured for a tool / engine profile are absent, the executor degrades gracefully — it prints the instructions the operator would otherwise dispatch, and persists state so --resume continues from the next pending milestone.
