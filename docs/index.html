MDA Spec Framework

A spec-driven development framework for AI-assisted game development, built on the MDA framework (Mechanics, Dynamics, Aesthetics) by Hunicke, LeBlanc & Zubek. Authoring on the keyboard, operating in a UI — one engine driving both.

Get Started Learn the Concepts

The Problem

AI coding assistants can write game code, but they lack design intent. They implement features "in vacuo" — isolated from their effect on player experience. A damage system gets built without knowing it exists to create tension. A hint system gets tuned without knowing it serves discovery.

The Solution

Structure game design as layered, traceable specifications that give AI three things it normally lacks:

🎯

Intent

Aesthetic specs explain why a feature exists — which of the 8 player experience categories it serves.

📚

Constraints

Dynamic specs define behavioral boundaries and feedback systems that must emerge from the mechanics.

✅

Testability

Mechanic specs provide acceptance criteria, and runtime logs validate invariants and aesthetic proxies automatically.

How It Works

Every game feature is specified across the MDA causal chain before code is written. The example below is the running dogfood game — see specs/concept/cozy-hide-and-seek.concept.md in the repo for the full cascade. 

Game Concept          "A cozy hide-and-seek round for 2-4 friends, 60s rounds"
      |
      v
Aesthetics (WHY)      "The round should feel like playing together as a single
      |                 social unit, even though the surface is competitive."
      |                 Primary: Fellowship | Secondary: Sensation
      v
Dynamics (WHAT)       "A 60-second timer caps the round so no hider stays hidden
      |                 forever; on find, the hider becomes next round's seeker
      |                 so nobody is ever eliminated."
      v
Mechanics (HOW)       "Rule 4: Find Detection fires when seeker is within
      |                 findRange studs AND has line-of-sight AND presses
      |                 interact. findRange = TUN-001."
      v
Tuning (BALANCE)      "findRangeStuds: 8 [5-15], sensitivity: High
      |                 roundDurationSeconds: 60 [45-90], sensitivity: High"
      v
Assets (CONTENT)      "Cozy hiding-spot variants: 5 distinct silhouettes,
                        pastel palette, < 1500 tris each. Status: concept."

AI reads top-down (M→D→A) to understand intent when implementing. AI reads bottom-up (A→D→M) to trace problems when debugging.

Front door — hybrid

The framework has two equally-valid entry points that share one engine:

📝

Authoring (CLI + Wizard)

npx mda and npm run spec scaffold, validate, and gate the markdown specs under specs/ and design/. Files are the source of truth and live in version control. Solo developers stay here.

💻

Operating (MDA Studio)

A team-facing service that holds the state the CLI can't — registered games, issues, costs, approvals, asset-plan execution. Reach for it when more than one person needs the same view, or when state has to survive a restart.

The studio drives the CLI as a subprocess via the mda-runner service — it never re-implements validators, gates, or scaffolding. Editing tools/src/*.ts changes both surfaces immediately because there is no build step (the shim at tools/bin/mda.cjs runs the TypeScript through tsx). See Decisions · D0.1 for the rationale.

What's in the box today

🛠

CLI tooling

Validate specs, run quality gates, and scaffold new specs from the command line. Every command supports --json so external programs (including the studio) can drive it. See CLI Reference.

🧮

Guided wizard

npm run spec walks Concept → Aesthetics → Dynamics → Mechanics → Assets → Tuning → Levels with branching prompts and frontmatter pre-fill.

🗺

Level composition

Level specs orchestrate existing M·D·A primitives into spatial and temporal arrangements — blockouts, beat charts, encounters, and affordances.

🌕

Operator studio

Register a game from the UI, validate via subprocess, scaffold from inline CTAs, drive the asset-plan pipeline, and watch the spec tree update live via SSE. Pglite-backed persistence is built in. See MDA Studio.

📊

Structured logging

MDALogger tags every runtime event with its MDA layer and spec ID for traceable debugging. Filter by cid=N to trace a full causal chain across M·D·A.

🔗

Full traceability

Bidirectional links between all spec layers. Every mechanic traces to a dynamic and an aesthetic. The validator catches drift on every run.

🚪

Quality gates

Automated checks ensure specs are complete before proceeding to the next layer. Gates read the markdown body, not just frontmatter.

🤖

AI-optimised

Designed for AI assistants to read and implement with full design context via CLAUDE.md.

What's deferred

Two pieces are intentionally not in tree today:

  • Multi-engine bindings. Roblox is the only engine the framework targets today. The binding schema and parked rule stay in tree for cheap revival. See Decisions · D0.2 and Multi-Engine Support.
  • Agent runtime. The studio's persistent state and the engine adapter (mda-runner) shipped in V1-lite; the agent scheduler, watchdog, and cost budgets are M3+ work. See Decisions · D0.4.

Based On

MDA: A Formal Approach to Game Design and Game Research by Robin Hunicke, Marc LeBlanc, Robert Zubek (GDC 2001-2004).
