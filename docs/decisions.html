Decisions

Architecture Decision Records (ADRs) capture the rationale behind every load-bearing choice in the framework. Each record names the question, the chosen path, the rejected alternatives, and the trigger that re-opens the decision.

ADRs live in the repository under design/decisions/. Every record is dated; the date is the record's identity. To revise a decision, write a new ADR that supersedes the old one rather than editing in place — the history is the evidence.

V1-lite decisions (2026-05-27)

The five decisions below were captured before Week 1 of the V1-lite cut and shape every subsequent commit on this branch.

D0.1 — Front door: hybrid

The MDA Framework has two equally-valid entry points: the mda CLI for solo authoring and MDA Studio for team operations. The studio drives the CLI as a subprocess (one engine, two front doors). Studio-first is the long-term goal but premature today — agents and persistence had to land first.

Trigger to revisit: when the studio's agent runtime (M3) lands, the CLI becomes a back-end rather than a front door for most users.

File: design/decisions/2026-05-27-front-door.md

D0.2 — Multi-engine: deferred

Roblox is the only engine the framework targets today. The binding directory (specs/bindings/) has no instances; the binding-coverage validator rule has nothing to enforce. Multi-engine work re-opens when a real second-engine target arrives with a motivating game attached.

The rule code stays in tree (parked under _deferredRules) so re-enabling is a one-line change.

Trigger to revisit: a real game ships against a second engine target.

File: design/decisions/2026-05-27-multi-engine.md · see also Multi-Engine Support.

D0.3 — Embedded DB: pglite default

The studio's embedded persistence uses pglite (in-process Postgres-on-Wasm). Smaller blast radius than patched embedded-postgres, no native compilation on WSL or Windows, and the same SQL dialect as the external Postgres path. embedded-postgres remains opt-in behind MDA_STUDIO_DB_DRIVER=embedded-postgres for users who want native performance and have a working build.

Trigger to revisit: if pglite proves slow at the studio's actual write volumes once agent run telemetry lands.

File: design/decisions/2026-05-27-embedded-db.md

D0.4 — V1-lite is the intermediate cut

Persistence + the engine adapter + an onboard CLI but no agents. Six weeks of work. The full V1 (agents, scheduler, watchdog, cost budgets) is post-V1-lite, picking up at M3 of the studio plan.

Status: SHIPPED 2026-05-28. See Studio architecture for what landed and the studio plan in the repo for what's next.

File: design/decisions/2026-05-27-v1-lite.md

D0.5 — Dogfood before more surface area

Authoring one real game end-to-end forces every CLI / wizard / schema friction to surface before more features pile on top. The chosen game is a 60-second cozy hide-and-seek prototype, now living under specs/concept/cozy-hide-and-seek.concept.md with the full M / D / A cascade.

The friction the build surfaced is captured as a living log at design/decisions/2026-05-27-dogfood-log.md — it is the backlog for the next round of CLI / wizard / schema fixes.

Files: design/decisions/2026-05-27-dogfood-target.md, design/decisions/2026-05-27-dogfood-log.md

Where ADRs live in the repo

Every record is a self-contained markdown file. The naming convention is YYYY-MM-DD-slug.md; the date is the record's identity and never changes. 

design/
├── decisions/
│   ├── 2026-05-27-front-door.md
│   ├── 2026-05-27-multi-engine.md
│   ├── 2026-05-27-embedded-db.md
│   ├── 2026-05-27-v1-lite.md
│   ├── 2026-05-27-dogfood-target.md
│   └── 2026-05-27-dogfood-log.md      ← living friction log
├── roadmap/
│   └── multi-engine.md                 ← parked roadmap (was IMPROVEMENTS.md)
└── walkthroughs/
    └── v1-end-to-end.md                ← scripted authoring pass

When to write a new ADR

Write one whenever a choice would surprise a contributor reading the code six months later. Concretely:

  • A new dependency or runtime is adopted.
  • An existing decision is reversed or scoped down.
  • A non-obvious trade-off is made between two reasonable options.
  • A piece of code is left in tree as a parked option (so future readers know it's intentional, not dead).

The record's job is to make the rejected options visible. A bare "we chose pglite" is less useful than "we chose pglite because the embedded-postgres native build kept breaking on WSL".
