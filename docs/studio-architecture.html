Studio Architecture

How the spec-tree-first operator surface is built — the wire contracts, the server services, the UI composition, the data-flow guarantees, and the extension points.

Who this page is for

Developers extending the studio. If you just want to use the studio day-to-day, read the Operator Guide instead. Both pages assume you've seen the overview.

The five packages

The studio is a pnpm workspace with five packages, each with a single concern. V1-lite added the db and cli packages to the original three. 

+-------------------------------------------------------------+
|                @mda-studio/ui  (Vite + React)               |
| components / hooks / lens model / SSE consumer / URL state  |
|  ^                                                          |
|  |  fetch + EventSource over /api  (Vite proxy -> :3100)     |
|  v                                                          |
| @mda-studio/server  (Express + tsx)                         |
| routes / services / stores (memory|db) / mda-runner /       |
| spec-watcher / SSE publisher                                |
|  ^                                  ^                       |
|  |  workspace:* imports             |  subprocess via       |
|  v                                  |  npx mda --json       |
| @mda-studio/shared  (TypeScript + zod)        +-------------+
| wire schemas + MDA vocabulary +               |  mda CLI    |
| CLI JSON contracts (mda-cli.ts)               |  (tools/)   |
|                                               +-------------+
| @mda-studio/db                                              |
| resolveDatabaseConfig (pglite|pg) + drizzle schema +        |
| createClient                                                |
|                                                             |
| @mda-studio/cli  (mda-studio onboard)                       |
+-------------------------------------------------------------+

Three rules hold this together:

  1. The wire contract is the only shared code. Every payload that crosses HTTP or SSE has a zod schema in @mda-studio/shared. Both the server and the UI import the parser. Drift on one side fails the typecheck or the runtime validation on the other.
  2. The CLI is the only engine. The server never re-implements validators, gates, or scaffolding. It spawns npx mda <cmd> --json via the mda-runner service and parses the output through the shared CLI schemas (also in @mda-studio/shared, so drift breaks one test suite immediately).
  3. No layer reaches over its peer. UI never imports server code; server never imports UI code. Both depend on shared; the server additionally depends on db.

Request lifecycle — opening a game

End-to-end trace of what happens between "operator clicks a game card" and "the spec tree appears with live updates wired up".

1. Chrome reads the URL

App.tsx reads game via useUrlSearchParams. Clicking a card calls openGame(id) which pushes a new URLSearchParams with game=<id>. The router (vanilla history.pushState) re-renders.

2. The tree fetch

GameContainer mounts and calls useSpecTree(gameId):

  1. Sets state to { status: "loading" }
  2. Fires fetch(`/api/games/${gameId}/spec-tree`)
  3. On 200: runs specTreeResponseSchema.safeParse(json)
  4. On any failure: looks up FALLBACK_BY_GAME and renders the bundled fixture with source: "fixture"

3. The server side

  1. getGame(gameId) — pulls from the in-memory games-registry. 404 if unknown.
  2. ensureCache(gameId, specsRoot) — rebuildSpecCache walks six directories under the workspace, parses frontmatter via spec-parser.ts, classifies each spec's layer + canonical / secondary parents per layer rules (decision D1).
  3. buildTreeResponse composes the response from findActiveIssueForSpec, computeCostRollup, and listValidatorWarnings.
  4. assembleSpecTreeResponse zips them into one SpecTreeNode array sorted by specId.

4. UI render

GameView receives the parsed response and computes lensResult = applyLenses(tree.nodes, lenses) — pure model producing three sets (visibleSpecIds, ancestorSpecIds, matchingSpecIds) — then renders LensBar, SpecTree, optional NodeDrawer, and the CommandPalette.

5. SSE subscription

In parallel, useStudioEvents opens an EventSource on /api/studios/default/events only if tree.source === "api" (no SSE in fixture mode).

6. Drawer open

Clicking a row writes node=<specId> to the URL. useSpecNodeDetail fetches GET /api/games/:id/spec-tree/node/:specId which returns the drawer bundle (spec body, issues, comments, work products, costs, trace) in one round trip.

@mda-studio/server

The boundary

routes/ are thin Express handlers that parse params/body, call a service, and shape the response. services/ hold business logic + state with no Express types. Each service is unit-testable in isolation; the routes get integration tests against createApp().

Stores: facade + factory + memory / db

Each operational store has three files under services/stores/:

  • <name>-store.ts — an interface plus a tiny factory that picks memory or db based on MDA_STUDIO_PERSISTENCE.
  • <name>-store-memory.ts — pure in-process impl with plain Maps. Fast tests; nothing survives a restart.
  • <name>-store-db.ts — Drizzle-backed impl using the sql tagged-template helper so the same SQL works against pglite and node-postgres.

The legacy free-function files (games-registry.ts, issues-store.ts, cost-events-store.ts, approvals-store.ts) are now facades: each holds a sync shadow Map for the read path, schedules an async write-through to the configured store, and exposes a rehydrate*FromStore() function that server/src/index.ts calls on boot to repopulate the shadow. Routes never await — they keep their existing sync imports.

StoreMemory shapeDB shape
games-registryMap<gameId, GameRegistration>games table
spec-cacheMap<gameId, CacheEntry> rebuilt on demand from disk(stays memory; rebuilt from specs/)
issues-storeMap<id, IssueSummary> + comment / work-product mapsissues table (comments + work-products stay in-process until the schema for them lands)
cost-events-storeMap<id, CostEvent> with monotonic COST-NNN idscost_events table

One services/stores/stores.contract.test.ts file parameterises every behavior test across both impls (16 tests: 8 memory + 8 db).

Driving the engine: mda-runner

services/mda-runner.ts is the only piece of code that knows how to spawn the CLI. The generic runMda<T> function:

  1. Spawns npx mda <args> (override the binary with MDA_BIN for tests).
  2. Buffers stdout / stderr.
  3. Streams NDJSON to an optional onEvent callback (used by asset-plan exec to surface live progress).
  4. Parses the last non-empty stdout line through a caller-supplied zod schema (from @mda-studio/shared).

Per-command helpers: runValidate, runGate, runNew, runAssetPlanGenerate, runAssetPlanExec, runAssetPlanImport. Adding a new command means: extend tools/src/cli.ts, add a zod schema in @mda-studio/shared, add a helper here, call from a route.

Spec liveness: spec-watcher

services/spec-watcher.ts attaches a chokidar watcher per registered game. Files added, changed, or deleted under specs/**/*.md or design/levels/**/*.md publish a node-changed studio event with the game id; the UI's SSE consumer invalidates the relevant queries.

Filenames starting with _ (schema files) and files without a .md extension are filtered out. WSL and Windows hosts auto-enable polling mode because native fsevents are unreliable on the 9P-backed filesystem.

The @mda-studio/db package

resolveDatabaseConfig reads three env vars:

  • DATABASE_URL — if set, returns { kind: "external", url }.
  • MDA_STUDIO_DB_DRIVER — otherwise picks the embedded driver: pglite (default) or embedded-postgres (opt-in; not yet wired).
  • MDA_STUDIO_INSTANCE — picks which directory under ~/.mda-studio/instances/ stores the embedded DB.

createClient(config) returns a typed DbClient with a Drizzle instance over node-postgres (external) or pglite (embedded). Five tables defined: studios, games, issues, cost_events, approvals. Migrations live under packages/db/drizzle/ and are applied with pnpm --filter @mda-studio/db db:migrate.

The SSE publisher

studio-events.ts is a tiny pub/sub: stores call publishStudioEvent(event) after every successful mutation; the SSE route subscribes a Response stream. Every connected client gets every event. 

type StudioEvent =
  | { type: "node-changed";          gameId: string; specId: string }
  | { type: "issue-status-changed";  gameId: string; specId: string; issueId: string }
  | { type: "cost-event";            gameId: string; specId: string | null }
  | { type: "validator-run-completed"; gameId: string }
  | { type: "approval-changed";      studioId: string; approvalId: string };

The activity-log writer subscribes too — every event becomes a row in the log, so the slide-out is a free byproduct.

The choice is deliberate: anything reachable via a shared link goes in the URL. Anything per-user / per-tab goes local. Anything fetched goes in a hook so it can refetch.

The hook pattern

Every server-resource hook has the same shape:

export function useThing(opts): {
  status: "idle" | "loading" | "ready" | "error";
  data: ThingResponse | null;
  error: string | null;
  refetch: () => void;
}

Fetches via fetch, parses with the matching zod schema, exposes a stable refetch() so the SSE handler can invalidate without remounting.

The lens model

lib/lenses.ts is pure:

parseLenses(URLSearchParams) -> ActiveLenses
applyLensPatch(URLSearchParams, Partial<ActiveLenses>) -> URLSearchParams
applyLenses(nodes, lenses) -> {
  matchingSpecIds:  Set<string>,  // pass the filter
  ancestorSpecIds:  Set<string>,  // need to stay visible to keep context
  visibleSpecIds:   Set<string>,  // matches union ancestors
}

SpecTree accepts these three sets as props. The component itself has no knowledge of lenses — it just hides everything not in visibleSpecIds and force-expands ancestorSpecIds. This is why the same component renders filtered and unfiltered views without branching.

Algorithms worth understanding

DAG-to-tree projection (decision D1)

Many specs have multiple traces_to_* parents. The plan picks the first parent in the relevant array as the canonical parent; everything else is secondary.

LayerCanonical comes fromSecondary
A——
Dtraces_to_aesthetics[0]traces_to_aesthetics[1..]
Mtraces_to_dynamics[0]...[1..] + all traces_to_aesthetics
ASTtraces_to_mechanics[0]...[1..] + all traces_to_aesthetics
TUNEtraces_to_mechanics[0]...[1..] + dynamics + aesthetics
LEVEL— (parallel root)— (refs land in outgoingRefSpecIds)

Cost rollup — the no-double-count invariant

services/cost-rollup.ts computes own + subtree cents per spec:

  1. own[spec] = sum of cost events with billingCode === spec in the current month (MTD).
  2. subtree[spec] = own[spec] + sum of subtree[child] for every canonical-parent child only. Secondary parents never see the cost.

This guarantees that summing subtree[root_A_specs] equals total_attributed_cents. Orphan events (billingCode === null) contribute to the game total but never to any spec's rollup.

The "keep ancestors visible" lens filter

When a user filters by ?layer=M, the tree should still show the path AES-001 > DYN-001 > MEC-001 — otherwise context evaporates. applyLenses:

  1. Compute matching = nodes that pass every lens
  2. Walk each match upward via canonicalParentSpecId collecting ancestors
  3. visible = matching union ancestors
  4. ancestorSpecIds is returned separately so the tree can force-expand those rows

Live updates end-to-end

[mutation in any store]
        |
        v
publishStudioEvent(event)            <- server (studio-events.ts)
        |
        +-- activity-log-store.ts -> ring-buffer push
        +-- studioEventsRouter -> res.write("data: ...\n\n")
                |
                v
        EventSource (UI, useStudioEvents)
                |
                v
        handleStudioEvent (App.tsx) -> refetch the relevant hook(s)
                |
                v
        useSpecTree.refetch | useSpecNodeDetail.refetch
        useApprovals.refetch | useActivity.refetch

Two non-obvious properties:

  1. Idempotent invalidation. Refetch hooks bump an integer; calling them repeatedly during a burst of events causes one fetch per useEffect cycle, not one fetch per event.
  2. Fixture mode disables SSE. useStudioEvents({ enabled }) is false when the tree fell back to fixture data — there's no live server to subscribe to.

Test strategy

Four layers, each with a different job.

Unit tests (vitest)

Every *.ts and *.tsx has a sibling *.test.ts(x). Coverage is gated per package at ≥ 80% lines / statements / branches / functions in vitest.config.ts.

A11y tests (vitest-axe)

src/test/a11y.test.tsx renders every chrome-reachable surface and runs axe-core against the DOM. Violations fail the test. The region and color-contrast rules are disabled with rationale — they false-positive in jsdom-isolated components, and Lighthouse covers them with real layout.

End-to-end (@playwright/test)

playwright.config.ts boots the API server (with the fixture studio registered via env) + the Vite dev server via Playwright's webServer array. e2e/smoke.spec.ts exercises: studio home → tree → deep-linked drawer → issue status edit → every chrome nav surface, the seeded approvals queue, free-text lens, and the command palette.

Performance (@lhci/cli)

lighthouserc.json asserts a desktop budget:

LCP        ≤ 2500 ms
TBT        ≤  200 ms
CLS        ≤  0.1
JS weight  ≤  600 KB
perf score ≥  0.85
a11y score ≥  0.9

Extension points

Add a server route

  1. Add the request / response shape to @mda-studio/shared as a zod schema + type, and ship a round-trip test
  2. Build a service in server/src/services/ with its own unit tests
  3. Add the route file in server/src/routes/ — thin handler that parses params + body, calls the service, returns the parsed shape
  4. Mount it in app.ts
  5. If it mutates, publish a StudioEvent after the store write

Add a UI surface

  1. Build a useThing hook in ui/src/hooks/ mirroring the existing hooks' shape
  2. Build the panel in ui/src/components/<Thing>Panel.tsx, using existing tokens for colors
  3. Add CSS to ui/src/styles/app.css
  4. Wire view=thing in App.tsx's body switch
  5. Add onOpenThing / Thing button to Chrome.tsx and App.tsx
  6. Add an entry to the a11y test (src/test/a11y.test.tsx)
  7. (Optional) Extend the Playwright smoke spec

Add a lens

  1. Extend ActiveLenses in lib/lenses.ts + parseLenses + applyLensPatch + the filtering predicate inside applyLenses
  2. Add a chip case in LensBar.tsx
  3. Add a clear-key in App.tsx clearLens
  4. Update lib/lenses.test.ts and the KeymapHelp overlay

Add a status / layer

The MDA vocabulary is fixed in V1. To extend:

  1. Add the value to MDA_LAYERS / SPEC_STATUSES / STATUSES_BY_LAYER in shared/src/mda.ts
  2. Add a glyph + color token in the same file and matching CSS variable in ui/src/styles/tokens.css
  3. Add the prefix in ID_PREFIX_TO_LAYER and update layerFromSpecId
  4. Update spec-parser.ts defaults if the new layer has a different default status
  5. Run pnpm typecheck — exhaustive switch statements on the union will fail until handled

Add an SSE event type

  1. Add the case to the union in shared/src/studio-events.ts
  2. Publish it from the relevant service
  3. Handle it in GameView.handleStudioEvent — decide which queries to invalidate
  4. Add to the activity-log writer if the event should also become a visible log row

Where the seams point next

Persistence

Every in-memory store has a method-shaped public API exactly so it can be swapped for a Drizzle module:

  1. Add the table to packages/db/src/schema/
  2. Replace the store's Map<...> internals with db.insert/select
  3. Leave the route file untouched; rerun the route's integration test against an embedded Postgres

Tables waiting in system.md:

  • spec_frontmatter_cache (the spec-cache module)
  • issues, issue_comments, issue_work_products
  • cost_events
  • validator_runs
  • approvals
  • activity_log

Typed SSE client

Today the client casts JSON to StudioEvent. A small codegen step could give the publisher a typed publish<T extends StudioEvent>(event: T) overload so an exhaustive switch on the UI side is unmissable.

Persistent lens presets

Tree expansion already persists in localStorage. Saved lens presets were intentionally deferred — URL-only for V1. The hook boundary in lib/lenses.ts is the right place to add named-preset read / write.
